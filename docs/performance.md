# Performance, Benchmarking, and Regression Policy

This document defines the benchmarking architecture, deterministic dataset standards, mathematical parity gates, and regression governance rules for `ta-crypto`.

---

## 1. Objectives and Philosophy

`ta-crypto` enforces three primary performance principles:

1. **Parity Before Performance**: No performance optimization or speedup metric is valid unless mathematical parity against the batch reference is proven point-by-point within numerical tolerance.
2. **Deterministic Reproducibility**: All benchmark datasets are generated with a documented PRNG seed. `Math.random()` is prohibited in official benchmark and regression suites.
3. **Algorithmic Correctness over Micro-Timing**: CI gates prioritize algorithmic complexity invariants ($O(N)$ vs $O(N^2)$) and streaming speedup ratios over noisy absolute wall-clock timings across disparate virtualized runners.

---

## 2. Deterministic Dataset Generation

All benchmark datasets are generated by `scripts/bench/dataset.js` using a Mulberry32 32-bit pseudorandom generator (`scripts/bench/prng.js`):

- **Canonical Seed**: `0x43525950` (`1129466192` in decimal).
- **Financial Invariants**:
  - Open, High, Low, and Close are strictly positive ($P_t > 0$).
  - High is strictly bounded by wicks: $\text{high}_t \ge \max(\text{open}_t, \text{close}_t)$.
  - Low is strictly bounded: $0 < \text{low}_t \le \min(\text{open}_t, \text{close}_t)$.
  - Volume is strictly non-negative ($\text{volume}_t \ge 0$).
- **Standard Dataset Sizes**:
  - `RECOMPUTE_SMALL` (2,000 candles): Used for stateful streaming versus naive batch recomputation comparisons ($O(N^2)$ simulation).
  - `STANDARD_10K` (10,000 candles): Standard batch indicator baseline.
  - `LARGE_100K` (100,000 candles): Scaling stress tests and high-throughput streaming evaluation.

Running the suite with the same seed guarantees byte-for-byte identical datasets across all platforms and runs.

---

## 3. Measurement Harness & Statistical Method

Execution timings are measured by `scripts/bench/harness.js`:

- **Warmup Policy**: 3 warmup runs (5 for baseline generation) execute before measurement to trigger V8 compilation, inline caching, and JIT tier-up. Warmup runs are not included in timing metrics.
- **Sample Count**: 7 measured sample runs (15 for baseline generation).
- **Primary Metric**: **Median Runtime (`medianMs`)**. The median filters out transient garbage collection (GC) pauses and OS thread preemption.
- **Auxiliary Metrics**: Min, Max, Mean, Standard Deviation, and Operations/sec ($\text{datasetSize} / (\text{medianMs} / 1000)$).
- **Result Validation**: Timings producing non-finite values (NaN, Infinity) or non-positive durations are treated as immediate hard failures.

---

## 4. Mathematical Parity Gate

Before timing measurements begin, `scripts/bench/parity.js` runs a comprehensive parity check comparing all stateful streaming constructors against their batch API equivalents:

- **Tolerance**: $1 \times 10^{-10}$ for stateful/batch parity; $1 \times 10^{-9}$ for rolling vs legacy two-pass variance rounding.
- **Discrete Exactness**: Discrete indicators such as `volatilityRegime` (-1, 0, 1, null) must match exactly.
- **Composite Outputs**: MACD (`macd`, `signal`, `histogram`) and Bollinger Bands (`basis`, `upper`, `lower`) are evaluated across all components.
- **Fail-Fast Rule**: If any point diverges or null alignment mismatches, **the benchmark aborts immediately**. No timing or speedup metrics are reported for invalid outputs.

---

## 5. Stateful Streaming vs Naive Batch Recomputation

Real-time streaming pipelines traditionally suffer when forced to recompute batch indicators over growing historical arrays for each new candle:

$$\text{Naive Batch Recomputation: } O(N^2) \text{ operations}$$
$$\text{Stateful Streaming: } O(N) \text{ total operations } (O(1) \text{ per tick})$$

`scripts/bench-stateful.js` measures both approaches on a controlled dataset of 2,000 candles:

| --- | --- | --- | --- | --- | --- |
| `createSMA(20)` | 2,000 bars | ~11.8 ms | ~0.05 ms | **~210x** | PASS |
| `createEMA(20)` | 2,000 bars | ~13.4 ms | ~0.03 ms | **~420x** | PASS |
| `createRSI(14)` | 2,000 bars | ~17.5 ms | ~0.04 ms | **~370x** | PASS |
| `createMACD(12,26,9)` | 2,000 bars | ~59.8 ms | ~0.07 ms | **~850x** | PASS |
| `createATR(14)` | 2,000 bars | ~42.5 ms | ~0.06 ms | **~620x** | PASS |
| `createBBANDS(20,2)` | 2,000 bars | ~35.8 ms | ~0.08 ms | **~450x** | PASS |
| `createRealizedVolatility(30)` | 2,000 bars | ~28.2 ms | ~0.09 ms | **~300x** | PASS |

## 6. Algorithmic Scaling Guard (10k vs 100k)

To guarantee that internal rolling algorithms in `src/core/rolling.ts` maintain $O(N)$ complexity and do not regress to repeated window scanning ($O(N \cdot K)$ or $O(N^2)$), the suite evaluates the runtime growth ratio from 10,000 to 100,000 items ($10\times$ data expansion):

$$\text{Growth Ratio} = \frac{\text{medianMs}(100\text{k})}{\text{medianMs}(10\text{k})}$$

- **Ideal $O(N)$ Scaling**: ~7x to 25x on bare-metal CPUs; up to ~40x on virtualized cloud VMs with GC sweeps.
- **Maximum Allowed Threshold**: **$\le 50\times$**.
- **Quadratic Regression Guard**: A rescan algorithm would scale $\approx 100\times - 200\times$, immediately triggering a `FAIL` status.

## 7. Versioned Baseline & Regression Policy

Reference baseline metrics are recorded in [`bench/baseline.json`](../bench/baseline.json).

### Regression Status Classification

$$\Delta\% = \frac{\text{candidateMedianMs} - \text{baselineMedianMs}}{\text{baselineMedianMs}} \times 100\%$$

| Status | Delta Threshold | Meaning & Action |
| --- | --- | --- |
| **`PASS`** | $\le +15.0\%$ | Within standard execution noise or faster. |
| **`WARN`** | $+15.0\%$ to $+35.0\%$ | Moderate variance; flagged for observation, does not fail standard CI. |
| **`FAIL`** | $> +35.0\%$ | Significant regression detected; release blocker unless justified. |

### Baseline Update Policy

Updating `bench/baseline.json` is an explicit, human-authorized engineering action:

```bash
npm run bench:update-baseline
```

`npm run bench:regression` **never** modifies the baseline file.

---

## 8. Runner Noise & Rerun Policy

Virtual machines and CI runners (e.g. GitHub-hosted runners) experience CPU throttling, virtualization jitter, and noisy neighbor interference.

Rules for interpreting results:
1. **Never "Retry Until Green"**: Do not loop test executions repeatedly hoping for a lucky run.
2. **Relative Invariants Over Absolute Timing**: If absolute timings fluctuate between CI runs, verify that:
   - Parity gate is `PASS`.
   - Scaling ratio ($100\text{k} / 10\text{k}$) is $\le 35\times$.
   - Streaming speedup over batch recompute is $\ge 1.0\times$.
3. **Cross-Machine Comparisons**: Absolute numbers on Apple Silicon, AMD EPYC, and Intel Xeon cannot be compared directly. Use deltas against a machine-local baseline when benchmarking local optimizations.

## 9. Benchmark Commands

```bash
# Exploratory benchmark across 10k candles
npm run bench

# Rolling engine vs legacy rescan comparison (10k and 100k)
npm run bench:rolling

# Stateful streaming vs naive batch recomputation
npm run bench:stateful

# Full regression check against bench/baseline.json
npm run bench:regression

# Output machine-readable JSON
node ./scripts/bench-regression.js --json

# Explicit baseline update (requires human authorization)
npm run bench:update-baseline
```
